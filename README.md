# Task Management API

REST API для спільної роботи із задачами. Користувачі можуть створювати задачі, призначати виконавців, змінювати статуси та залишати коментарі. Стек проєкту — FastAPI, Pydantic, SQLAlchemy Async, PostgreSQL, Alembic, Docker Compose і Pytest.

## Локальний запуск

Створіть `.env` із шаблону в корені проєкту:

- PowerShell — `Copy-Item .env.example .env`
- Bash — `cp .env.example .env`

```sh
docker compose up --build -d
```

Після запуску PostgreSQL контейнер `web` застосовує міграції Alembic і запускає API. Інтерактивна документація доступна на [localhost:8010/docs](http://localhost:8010/docs). Якщо порт зайнятий, задайте інший `API_PORT` у `.env`.

## Перша задача через Swagger UI

1. У `POST /auth/register` натисніть **Try it out** і створіть користувача, наприклад з тілом `{"username":"ostap","password":"Local-Demo-Password-42"}`.
2. Натисніть **Authorize** й введіть ті самі дані. Swagger викличе `POST /auth/login` і додасть JWT до наступних запитів.
3. Отримайте свій ID через `GET /users/me` або ID іншого виконавця через `GET /users`.
4. Створіть задачу через `POST /tasks`. Підставте ID виконавця і поточну або майбутню дату.

```json
{
  "title": "Додати звіт про задачі",
  "description": "Показати кількість задач за статусами",
  "priority": "high",
  "assignee_id": 1,
  "deadline": "2030-01-15"
}
```

У відповіді буде ID задачі та початковий статус `backlog`. Підставте ID в `PATCH /tasks/{task_id}/status` і надішліть `{"status":"in_progress"}`. Через `POST /tasks/{task_id}/comments` можна додати коментар із полем `text`.

Для клієнта поза Swagger надішліть `username` і `password` на `POST /auth/login` як `application/x-www-form-urlencoded`. Використовуйте отриманий `access_token` у заголовку `Authorization: Bearer <token>`. За замовчуванням токен дійсний 30 хвилин.

## Маршрути

| Метод і шлях | Що робить |
| --- | --- |
| `POST /auth/register` | Створює користувача |
| `POST /auth/login` | Видає JWT |
| `GET /users/me` | Повертає поточного користувача |
| `GET /users` | Повертає список користувачів для вибору виконавця |
| `POST /tasks` | Створює задачу |
| `GET /tasks` | Повертає список задач |
| `GET /tasks/{task_id}` | Повертає одну задачу |
| `PATCH /tasks/{task_id}` | Редагує поля задачі або змінює виконавця |
| `DELETE /tasks/{task_id}` | Видаляє завершену чи скасовану задачу |
| `PATCH /tasks/{task_id}/status` | Змінює статус |
| `GET, POST /tasks/{task_id}/comments` | Переглядає список коментарів або додає коментар |
| `GET /tasks/overdue` | Повертає активні задачі, дедлайн яких минув |
| `GET /tasks/stats` | Повертає загальну кількість задач і підрахунки за статусами та пріоритетами, а також кількість активних і прострочених |

Задачі спільні для зареєстрованих користувачів. Кожен може переглядати їх і коментувати. Автор може редагувати, призначати виконавця та видаляти задачу. Змінювати статус може автор або виконавець.

## Статуси й дедлайни

- Основний шлях — `backlog → in_progress → review → done`. Вручну можна скасувати задачу зі статусу `backlog` або `in_progress`. Заборонений перехід повертає `409 Conflict`.
- Для переходу в `done` потрібен виконавець і чинний дедлайн. У `review` змінювати виконавця вже не можна. У `done` і `cancelled` редагування закрите, а видалення доступне.
- Дедлайн — календарна дата `YYYY-MM-DD` в UTC. Поточна дата дозволена. Задача стає простроченою на початку наступного дня за UTC.
- На одного виконавця можна призначити до 10 активних задач. Активні статуси — `backlog`, `in_progress` та `review`. Назву Todo з правила про ліміт трактовано як Backlog. Перевірка ліміту використовує блокування рядка виконавця в PostgreSQL, щоб одночасні призначення не перевищили межу.
- Під час запуску API стартує фонова корутина. Вона за замовчуванням раз на 60 секунд переводить прострочені активні задачі в `cancelled`, зокрема з `review`. Інтервал задає `OVERDUE_CHECK_SECONDS`. Після скасування задача зникає з `/tasks/overdue` і залишається в загальному списку.

## Пошук, фільтри та сортування

```text
GET /tasks?search=звіт&status=backlog&priority=high&assignee_id=1&limit=20&offset=0
```

`search` шукає в назві й описі без урахування регістру. Дедлайн можна фільтрувати за точною датою (`deadline`) або включним діапазоном (`deadline_from`, `deadline_to`).

За замовчуванням першими йдуть `high`, потім `medium` і `low`. Усередині пріоритету спочатку показуються задачі з найближчим дедлайном. Для явного сортування задайте `sort_by=created_at`, `deadline` або `priority` і за потреби `direction=desc`.

Списки повертають `total`, `limit`, `offset` та `items`. За замовчуванням на сторінці 20 записів, максимум — 100.

## Тести

```sh
docker compose exec web python -m pytest -q
```

Тести піднімають API в процесі Pytest, застосовують міграції до окремої тимчасової схеми PostgreSQL і видаляють її після перевірки. Серед сценаріїв — JWT, права доступу, переходи між статусами, конкурентні призначення, коментарі, фільтри, статистика та автоматичне скасування прострочених задач.
